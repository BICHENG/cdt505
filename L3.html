L3 · 概念与区别

先确定项目范围

范围明确之后，才能知道需要分解哪些工作、估算多少工期和费用，以及由谁承担责任。

必考范围 · 概念与区别

先确定 Project Scope 项目范围，再分解工作、估算时间与费用。区分“成果有什么功能”与“团队要完成什么工作”。

产品范围与项目范围

Product scope / Project scope

Product scope 是产品或服务的特征与功能；Project scope 是为交付这些成果而需要完成的工作。范围管理要保证完成全部必要工作，并控制不属于项目的工作。

假设医院要交付一套预约系统。“患者能查询时段、预约和取消”描述系统应有的功能；“分析需求、开发、测试、培训并上线”描述团队为交付它要做的工作。前者是 Product Scope 产品范围，后者是 Project Scope 项目范围。

问题范围医院预约系统的例子
产品能做什么？Product scope 产品范围显示门诊时段、预约、取消预约
团队要做什么才能交付？Project scope 项目范围分析需求、设计、开发、测试、培训、上线

明确范围后，才能可靠地分解工作、安排人员、估算时间和费用。新增功能或工作需要评估并处理相应变更。

英文参考表达

Product scope describes the features and functions of a product, service or result. Project scope describes the work required to deliver it. Project scope management ensures that the project includes all the work required, and only the work required, for successful completion.

L3 · Requirement / Types of Requirements

需求及其类型

要确定范围，需要先知道为什么做这个项目、使用者需要什么、成果必须满足什么条件。“减少患者等待”和“系统允许取消预约”就属于不同层次的需求。

必考范围 · 老师明确举例：名词解释

Types of Requirements 需求类型要能列出六类并说明含义；Solution Requirements 解决方案需求继续分为功能与非功能需求。不增加需求改写任务。

需求的类型

Types of requirements

Requirement 是为满足业务需要或约定条件而必须具备的能力、条件或特性。需求类型按它说明的问题区分。

同一项目可以有不同层次的需求。医院为什么要做、护士需要什么、系统必须能做什么，问的是不同问题。先找题目描述的对象，再判断需求类型。

类型回答什么例子
Business requirements 业务需求组织为什么做减少患者预约等待
Stakeholder requirements 干系人需求具体相关方需要什么护士希望能查看当日预约名单
Solution requirements 解决方案需求成果具备什么功能或属性Functional：允许取消预约；Nonfunctional：指定负载下响应不超过 2 秒
Transition and readiness requirements 过渡与就绪需求怎样顺利切换和投入使用迁移旧数据；完成上线培训
Project requirements 项目需求项目执行需满足什么条件按规定时间交付进度报告
Quality requirements 质量需求以什么质量标准判断是否符合通过约定测试标准并记录检查结果
非功能需求描述性能、可靠性等属性；质量需求规定评价是否合格的标准。情景可能涉及多种需求，做单选时应按题干明确强调的对象判断。

例如“患者可以取消预约”说的是系统提供的能力，属于 Functional Requirement 功能需求；“在指定负载下，两秒内响应”说的是运行表现，属于 Nonfunctional Requirement 非功能需求。两者都在 Solution Requirements 解决方案需求之下。名词解释若问 Types of Requirements，要回答六类，不能只回答功能／非功能两类。

英文参考表达

Business requirements explain why the project is undertaken. Stakeholder requirements describe the needs of specific stakeholders. Solution requirements specify the product’s functional capabilities and nonfunctional attributes. Transition and readiness requirements support the move to the future state, such as data migration and training. Project requirements specify conditions that the project must meet. Quality requirements define criteria used to evaluate successful completion and compliance.

L3 · Project Scope Statement

项目范围说明书

把需求整理清楚后，还要约定本次交付哪些成果、哪些不做、怎样验收。Project Scope Statement 项目范围说明书记录这些边界，对应速记中的“范围承诺书”。

必考范围 · 范围说明

Project Scope Statement 项目范围说明书对应速记中的“范围承诺书”。六项内容要能区分，尤其是成果、验收标准、约束与假设。

项目范围说明书

Project scope statement

范围说明书写清成果边界，以及接受成果所依据的条件。它使团队和干系人对交付内容形成共同理解。

团队如果只说“交付预约系统”，仍可能不知道是否要做网上付款、培训多少人、怎样才算验收通过。范围说明书把这些边界和条件写清楚，后续才有一致的工作依据。

内容含义预约系统示例
Product scope description 产品范围描述成果有哪些特征与功能支持查询、预约和取消
Acceptance criteria 验收标准怎样判断可以接受在约定测试中正确保存和取消预约
Deliverables 可交付成果实际交付哪些结果可用系统、用户手册、培训材料
Exclusions 排除事项明确不包含什么本期不包含网上付款
Constraints 约束必须遵守的限制在指定日期前上线，预算有上限
Assumptions 假设计划时暂按成立处理的条件医院按计划提供合格的测试数据

Deliverable 可交付成果是交什么，例如可用系统；Acceptance Criteria 验收标准是按什么条件接受它，例如通过约定功能测试。Constraint 约束是必须遵守的限制；Assumption 假设是计划时暂按成立处理的条件。假设后来不成立，需要重新评估计划。

英文参考表达

A project scope statement includes the product scope description, acceptance criteria, deliverables, exclusions, constraints and assumptions. The product scope describes features and functions. Deliverables are the results to be provided, and acceptance criteria specify the conditions for accepting them. Exclusions identify what is outside the scope. Constraints are limits that must be respected. Assumptions are conditions treated as true for planning.

有了明确的验收标准，才能在成果完成后判断是否可以交付。这里接着区分“检查合格”和“客户正式接受”。

检查成果合格，与正式接受成果

Control Quality 控制质量 · Validate Scope 确认范围

范围说明书写下了成果和验收标准。完成工作后，测试人员先检查系统是否符合要求，客户再根据约定正式接受成果。这两种行为关注的对象不同。

行为对应概念
测试预约是否被正确保存，记录检查结果Control Quality 控制质量：检查成果是否符合质量要求。
客户按约定验收标准正式接受预约系统Validate Scope 确认范围：正式接受已完成的可交付成果。
英文参考表达

Control Quality checks whether deliverables meet their quality requirements. Validate Scope formalizes acceptance of the completed project deliverables.

L3 · 选择题概念

WBS、分解法与工作包

明确项目范围之后，团队要把需要完成的工作逐层分开，才能估算和分工。WBS 展示这种组成关系，最低层称为工作包。

必考范围 · 概念辨认

Decomposition 分解法用于构建 WBS；Work Package 工作包是最低层。会辨认分解步骤、100% Rule 百分之百规则及命名、编号规则。免画完整 WBS 大题，概念仍须掌握。

工作分解结构

Work Breakdown Structure (WBS)

WBS 是对项目全部工作范围的层级分解。Decomposition 分解法把较大的成果或工作逐步分成更小、便于管理的部分。

范围说明书已经确定要交付什么，接下来要把这些工作分成可以安排的部分。Decomposition 分解法就是逐层细分：上一级叫 Parent 父项，它下面拆出的各部分叫 Children 子项。

分解步骤在预约系统项目中怎样做
Identify and analyse deliverables and work
识别成果与相关工作		列出系统、用户手册、培训等约定成果，以及完成它们所需的工作。
Structure and organize the WBS
组织层级		把系统交付、上线准备、项目管理与收尾等工作分别归组。
Decompose upper levels
继续细分		把系统交付进一步分成预约功能、取消功能等便于管理的部分。
Assign identification codes
给各项编号		例如 1 是系统交付，1.1 是其中的预约功能。编号表示层级归属，不表示开始顺序。
Verify the degree of decomposition
检查分得是否合适		检查是否能估算工期与费用、分配责任、判断完成情况；过大则继续分，重复或只有同义子项则调整。

下面的 WBS 片段按这个思路组织。连线说明哪些工作组成上一级，工作先后顺序另用活动网络安排。

预约系统项目
├─ 系统交付
│　├─ 预约功能
│　└─ 取消功能
├─ 上线准备
│　├─ 数据迁移
│　└─ 人员培训
└─ 项目管理与收尾

这个层级片段说明“组成关系”。不能按方框左右位置推断哪个活动先做。

规则如何检查
100% Rule 百分之百规则同一父项下的子项合起来覆盖父项的全部工作
No duplication 不重复同一项工作不放进两个不同分支
没有遗漏包括必要的规划、管理和收尾
分解有意义避免一个父项下面只有一个同义子项
例子

把整辆汽车想成父项，各部件合起来应当组成完整汽车。少了必要部件，不能算完成；同一个部件重复列在两处，也会造成重复计算。项目的 100% Rule 百分之百规则同样要求子项完整覆盖父项约定的工作，包括必要的管理与收尾。

低层工作名称用动词写清动作，例如“开发预约功能”“测试取消功能”，英文可用 Develop、Test、Install 开头。完成后，还要对照 Project Charter 项目章程中获批的目标与要求，检查计划做的、采购的工作是否都已包括。

老师用 AON、WBS、Gantt Chart 三个名称提问的是：Decomposition 分解法用于构建哪一种图？答案是 WBS。这几个板书名称不能直接解释成老师要求背诵的三步流程。
英文参考表达

A WBS is a hierarchical decomposition of the total scope of work to be carried out by the project team. Decomposition breaks larger deliverables and work into smaller, more manageable components. The children of each parent must represent 100% of that parent’s work without duplication.

分解不能无限继续。团队已经能估算、分配责任并检查完成情况时，就可以把这一层作为工作包。下面用同一个预约功能说明工作包与后续活动安排的关系。

工作包

Work package

Work package 是 WBS 最低层级的工作，可据此估算成本和工期、分配责任并进行管理。

例子

“完成预约功能”若已小到可以估算、安排负责人并检查完成情况，可以作为工作包。它可能需要开发和测试人员合作；指定负责人不等于只能由一个人完成。

分解可按阶段、成果、工作类型、地点、费用、组织责任、服务或结果组织，选择能清楚表示项目范围的方式。工作包没有统一的“必须几天内完成”要求。

例如，“完成预约功能”可以作为工作包；排进度时，再列出设计、开发、测试等 Activity 活动并确定先后关系。WBS 说明项目由哪些工作组成；AON 安排这些活动直接等待谁；甘特图显示它们何时进行。

英文参考表达

A work package is the lowest-level component of a WBS. It contains work that can be estimated, assigned, monitored and controlled. One person may be accountable for the package while several people perform its work.

WBS 按概念、工作包和分解规则准备；不要求绘制完整 WBS 大题。

L3 · Organizational Breakdown Structure / Responsibility Assignment Matrix

OBS 与 RAM：确定责任归属

WBS 已列出需要完成的工作包。接下来还要决定哪个部门承担，以及每名成员具体负责什么。OBS 和 RAM 分别说明这两层责任。

必考范围 · 老师明确举例：RAM 名词解释

OBS 组织分解结构把工作对应到组织；RAM 责任分配矩阵把任务对应到人员及其责任。英文解释 RAM 时可配一个小表，说明行、列与符号。

组织分解结构

Organizational Breakdown Structure (OBS)

OBS 按组织或部门层级表示承担项目工作的人和单位。将工作包与组织单位对应，可以确定责任归属。

同一项目可能由软件部、数据部和培训部共同完成。先用 WBS 找出工作包，再用 OBS 确定哪个组织单位承担它，随后用 RAM 写清具体人员的责任。

项目承担单位
├─ 软件部 Software Department
├─ 数据部 Data Department
└─ 培训部 Training Department
WBS 中的 Work Package 工作包OBS 中的负责单位
完成预约功能软件部
迁移预约数据数据部
完成使用培训培训部

OBS 展示组织归属，这张对应表说明工作如何分给部门。部门承担一个工作包后，还需要进一步明确负责人和支持人员。

英文参考表达

An OBS is a hierarchical representation of the organizational units responsible for project work. It helps connect work packages with the departments or teams that carry responsibility.

“软件部承担预约功能”还没有说清具体谁做、谁批准。RAM 继续把任务与人员对应起来，并区分负责、支持、通知和批准等角色。

责任分配矩阵

Responsibility Assignment Matrix (RAM)

RAM 以任务为行、人员为列，表示每个人在任务中的责任。先读图例，再读交叉格。

RAM 也称 Linear Responsibility Chart 线性责任图。把 WBS 中需要分工的任务写成行，把参与人员写成列，再按图例标出每个人在该任务中的责任。下表中的符号各有含义，不能把所有参与者都当成负责人。

○ Responsible 负责　☆ Support 支持　■ Notification 通知　□ Approval 批准
任务项目经理开发工程师护士代表
确认预约规则□☆○
开发预约功能■○☆
验收预约功能□☆○

“开发预约功能”这一行表示开发工程师负责，护士代表支持，项目经理接收通知。空格表示表中未分配该角色。常见的 RACI 使用另一套字母，本题按这里给出的符号读写。

构建一个小 RAM：列出任务和人员，确定每项任务由谁负责，再填写支持、通知或批准角色，最后按行读一遍，检查是否存在无人负责的任务。问名词解释时，英文定义配这样的小表就能说明矩阵如何工作。

英文参考表达

A responsibility assignment matrix (RAM), also called a linear responsibility chart, links project tasks to team members and shows their roles. Tasks form the rows and people form the columns. The legend identifies responsibility, support, notification and approval.
