## 4.1 从需求到范围与WBS

WBS明确做什么，4.2确定谁负责和如何接受；5.1再用活动表表达顺序与工期。

### Requirement 需求

**Requirement · 需求**

为了满足相关方的需要，项目或交付成果必须具备的条件或能力。需求既可以描述功能，也可以描述性能、准备工作和管理要求。

可验证表达：对象＋指标＋阈值＋验证条件。

|需求类型|医院例子|
|---|---|
|Business requirement 业务需求|缩短患者到院后寻找服务窗口的时间。|
|Stakeholder requirement 利益相关者需求|接待人员能够查看当前等候人数。|
|Functional requirement 功能需求|患者可以领取号码，并在屏幕查看叫号。|
|Non-functional requirement 非功能需求|在规定负载下，叫号信息在2秒内更新。|
|Transition requirement 过渡需求|开放前完成接待人员培训和旧资料迁移。|
|Project / Quality requirement 项目／质量需求|每周提交进度记录；设备通过约定的验收测试。|


例子：两台终端同时使用、各测试50次，至少95%的取号请求在2秒内返回。

容易混淆的地方：功能回答能做什么；非功能要求回答在什么条件下达到怎样的表现。

### Product Scope / Project Scope 产品范围／项目范围

**Product Scope / Project Scope · 产品范围／项目范围**

产品范围描述成果的功能和特性；项目范围描述为了交付这些功能和特性而需要完成的工作。

**Project Scope Statement · 项目范围说明书**

对交付成果、验收标准、排除项、约束和假设作出明确说明，使参与者能据此判断某项要求是否属于当前项目。

范围说明：描述、交付物、验收标准、排除项、约束、假设。

|内容|产品范围|项目范围|
|---|---|---|
|医院接待区|两台取号终端、叫号显示、多语言提示|采购终端、安装接线、配置提示、测试并培训|
|范围排除项|本次不提供网上预约|本次不开展网上预约系统的开发和部署|


例子：多语言提示是产品特性；配置、测试和培训属于项目工作。

容易混淆的地方：约束是必须遵守的限制；假设是需要验证的规划前提。

### WBS 工作分解结构

**Work Breakdown Structure (WBS) · 工作分解结构**

把项目全部工作分解为较小、可管理部分的层级结构。每个子项进一步说明父项包含的范围。这里按交付成果组织接待区项目。

父项范围由其子项完整且无重复地覆盖。

|层级|编号与名称|包含内容|
|---|---|---|
|项目|1 接待区开放准备|本次接待区项目全部范围|
|主要部分|1.1 项目管理；1.2 可用设备；1.3 已安装指路牌；1.4 开放准备|分别管理、交付设备、交付标牌、准备投入使用|
|工作包示例|1.3.1 指路牌图样；1.3.2 已制作并安装的指路牌|进一步明确图样和现场成果|


例子：接待区分为项目管理、可用设备、已安装指路牌、开放准备。

容易混淆的地方：WBS表示包含关系；网络图表示活动依赖。

### 100% Rule 范围覆盖规则

**100% Rule · 100%规则**

每一层子项合计覆盖父项的全部范围，同一工作只计一次。100%指范围覆盖，不要求把所有工作换算成百分比或平均分配。

检查顺序：批准范围→遗漏→重复→父子归属→可分派程度。

例子：人员培训属于批准范围，即使不采购实物也需要纳入。

容易混淆的地方：100%不是预算花完，也不意味着每个分支平均分配。

### Work Package / WBS Dictionary 工作包／词典

**Work Package · 工作包**

WBS最低层能够分派、估算和控制的工作单元。一个工作包需要有清楚的成果和边界，例如交出六块按批准图样制作并安装好的指路牌。

**WBS Dictionary · WBS词典**

对WBS中各工作包的详细说明。词典把树图里放不下的范围、责任、资源、估算和验收要求写清，使执行者和接受者按同一理解工作。下面是一份词典条目的例子。

至少明确：做什么、交付什么、谁负责、资源与估算、如何验收。

|词典字段|1.3.2 指路牌制作与安装|
|---|---|
|范围与成果|按已确认图样制作并安装6块双语指路牌|
|包含与排除|包含制作、固定和现场核对；图样设计由1.3.1负责|
|责任与资源|现场负责人协调；制作商和安装人员执行|
|估算与依赖|预计2天；须先取得确认图样和可安装的墙面|
|验收条件|6处位置、两种语言、箭头方向与图样一致，固定情况通过检查|
|记录|保存图样版本、检查表、照片与接受记录|


例子：6块双语指路牌的制作安装包，排除已由设计包负责的图样设计。

容易混淆的地方：只写工作包名称，不能代替词典中的详细说明；分解深度也不是越深越好。

### Scope Baseline 范围基线

**Scope Baseline · 范围基线**

经批准的项目范围说明书、WBS和WBS词典。它提供执行与检查时共同使用的范围依据。

**Scope Management · 范围管理**

规划范围管理、收集需求、定义范围、创建WBS、确认范围和控制范围，共同维护项目应完成的工作。确认范围是正式接受已完成成果，控制范围则贯穿执行过程。

范围基线＝范围说明书＋WBS＋WBS词典。

|组成部分|说明什么|接待区例子|
|---|---|---|
|范围说明书|要交付什么，满足哪些条件|开放一楼接待区，提供取号和叫号服务|
|WBS，工作分解结构|范围怎样分成可管理的部分|设备、指路牌、开放准备和项目管理|
|WBS Dictionary，WBS词典|各部分的详细内容与边界|指路牌的地点、数量、语言、负责人及验收要求|


例子：增加一个服务窗口，先评估并批准，再更新涉及的范围、进度和预算。

容易混淆的地方：基线允许受控变更；不能不断覆盖原计划而失去批准记录。

### Work Package → Activity 工作包与活动

**Activity · 活动**

为完成项目成果而需要执行的具体工作。工作包可以包含一项或多项活动，活动应使用能看出做什么的名称。

工作包→具体活动→工期与紧前→网络图与排程。

|工作包|活动|工期与直接前置|
|---|---|---|
|指路牌图样|确认指路牌要求；设计指路牌|先确认要求，再设计|
|已安装指路牌|制作并安装指路牌|取得已确认图样后进行|
|已接受的接待区|检查设备和指路牌是否符合要求|设备与指路牌均准备好后进行|


例子：指路牌工作包包含设计、制作安装等活动。

容易混淆的地方：WBS包含关系不能直接当作活动依赖；编号相邻也不表示必须先后执行。

## 4.2 责任分工、验收与变更

明确范围和责任后，进度、费用与风险记录才能对应到同一项工作。

### OBS / RAM / RACI 组织与责任

**Organization Breakdown Structure (OBS) · 组织分解结构**

按组织或负责单位形成的层级结构，用于说明谁承担哪些工作和相关预算责任。

**Responsibility Assignment Matrix (RAM) · 责任分配矩阵**

将工作项与人员或组织交叉排列，标明各方负责、支持、审批或知会等关系。填写前先定义符号含义。

先读图例，再查执行、最终负责、征询和知会。

|工作项|设备组|标牌组|院方代表|
|---|---|---|---|
|设备安装|执行|—|接受|
|指路牌安装|—|执行|接受|
|联合检查|支持|支持|主持|


例子：设备组执行安装，院方代表按授权接受成果。

容易混淆的地方：符号不等于天然的职权；本练习每行一个A是明确采用的规则。

### 成本与责任归属

**Cost Account / Control Account · 成本账户／控制账户**

将特定工作范围与负责组织的成本管理联系起来。控制账户还用于综合管理范围、预算、进度和绩效，下面先练习明确成本归属。

组织汇总与工作明细都要核对；分摊金额合计等于原费用。

|WBS工作|OBS责任单位|预算（元）|实际（元）|
|---|---|---|---|
|取号终端|设备组|12000|12600|
|叫号屏|设备组|8000|7400|
|指路牌|标牌组|6000|6500|


例子：两项工作各偏差+600与−600，汇总为0仍需分别分析。

容易混淆的地方：此处费用差额为实际−预算，不能混用EV−AC。

### 责任接口与交接

把工作范围、提供者、接收者、条件和完成证据连接起来。

职责安排＋工作包边界＋交接与接受记录。

|交接事项|提供者|接收者|完成依据|
|---|---|---|---|
|终端与网络可用|设备组|测试负责人|安装配置记录及连通测试|
|双语图样确认|院方代表|标牌组|已批准图样版本|
|接待区正式移交|项目经理|院方运营负责人|验收清单、培训记录与设备资料|


例子：网络配置由明确的责任单位完成，再向测试负责人交接。

容易混淆的地方：有负责人的任务仍可能未完成；完成也不等于正式接受。

### Control Quality / Validate Scope 质量控制／范围确认

**Control Quality / Validate Scope · 质量控制／范围确认**

质量控制检查成果是否符合规定要求；范围确认由有权接受的一方正式接受已完成的交付物。检查记录可以成为接受的依据。

检查证据→按验收标准判断→授权接受或记录未接受事项。

|问题|质量控制|范围确认|
|---|---|---|
|关注点|设备是否通过功能和性能检查|院方是否正式接受这批设备|
|典型证据|测试结果、缺陷与复测记录|签署的接受记录，或拒绝原因|
|出现问题后|修复并复测|按约定处理未接受事项或提出变更|


例子：设备测试通过后，由院方授权代表按约定接受。

容易混淆的地方：新需求与原要求不符合要分别处理。

### Scope Control / Scope Creep 范围控制／范围蔓延

**Control Scope / Scope Creep · 范围控制／范围蔓延**

范围控制监测范围状态并管理基线变更。范围蔓延指未经相应控制、不断增加的范围；新增要求可以合理，但仍需明确影响与授权。

请求→影响分析→决定→更新通知→执行验证。

|步骤|增加窗口时处理什么|
|---|---|
|记录请求|谁提出、用途、数量、期望完成时间|
|分析影响|范围、依赖、成本、人员、质量与风险|
|取得决定|按授权程序批准、拒绝或暂缓，并说明条件|
|更新并通知|更新相关基线、采购和责任资料，保留版本|
|执行与验证|按批准内容完成，并检查和接受|


例子：免费增加屏幕仍可能需要电源、配置和验收工作。

容易混淆的地方：控制变更不等于拒绝所有变化；需要清楚的依据与授权。

### 范围管理综合判断

分别判断原要求不符合、新要求变更和完成证据缺失。

先找原批准条件，再判事件性质，最后安排责任与处理。

|事件|判断所需依据|
|---|---|
|方向箭头装反|批准图样、现场检查记录|
|新增第三台终端|原数量、请求用途、成本工期和资源影响|
|培训无记录|培训要求、参加人员、操作检查与接受标准|


例子：装反箭头要修正；新增终端要评估变更；培训要核对完成证据。

容易混淆的地方：不能用同一个标签替代不同原因和处理过程。

## 5.1 项目进度计划：从活动表到关键路径

### Project Scheduling · 项目进度计划

Project Scheduling（项目进度计划）是根据各项工作的工期与先后要求，安排开始和完成时间的过程。

例子：医院接待区准备开放时，设计师设计指路牌，工人制作并安装指路牌，另一组人员安装电脑和取号设备。负责人需要安排这些工作，并确定何时可以完成最后的检查。

容易混淆的地方：先确定工作内容与前置关系，再计算时间。调整图中方框的位置，不会改变工作之间的依赖。

### Activity / Duration · 活动与工期

**Activity · 活动**

项目中一项需要执行的具体工作。例如，给一家医院的服务台安装电脑和取号设备，就是一项活动。活动名称应当顾名思义，让人知道具体要做什么。

**Duration · 工期（历时）**

完成一项活动所需的时间。例如，设计师完成指路牌图样需要3天，这项活动的工期就是3天。

完成时间 = 开始时间 + 工期。

例子：设计师周二上午开始设计指路牌，周五上午完成。活动是“设计指路牌”，工期是3天，开始和完成时间分别为周二上午、周五上午。

容易混淆的地方：工期表示需要多久。工期为3天的工作从时点2开始，会在时点5完成。

### Predecessor / Successor · 前置与后续活动

**Activity Information · 活动信息表**

我们可以用一张表记录每项活动的名称、工期和前置关系。每行对应一项活动；阅读同一行，就能知道要做什么、需要多久，以及开始前要等哪些工作完成。

Finish-to-Start（FS）：后续活动的开始时间 ≥ 前置活动的完成时间。

例子：假设负责人先确认设备和指路牌的要求（A），设计师再设计指路牌（B），工人最后制作并安装指路牌（D）。顺序为A→B→D；B是D的紧前活动，A通过B间接影响D。

容易混淆的地方：Concurrent Activities（并行活动）可以分别进行，例如设计师设计指路牌时，另一组人安装设备。可以同时开始的工作，也可以在不同时间完成。

### 案例的工作安排和计时方式

**Gantt Chart / Milestone · 甘特图 / 里程碑**

甘特图用横轴表示时间，每条横条表示一项活动从开始到完成的区间。里程碑是重要事件，例如“接待区检查通过”，工期为0。检查工作需要1天，检查通过则是这项工作完成后的一个时点。

Finish-to-Start（FS）：前一项完成后，后一项才能开始。零滞后：没有额外规定的等待时间。工期单位为天，项目开始时记为0。

例子：负责人用2天确认要求，在时点2完成。设计师随即开始设计，工作3天，在时点5完成。

容易混淆的地方：计算中按连续时间安排，所需人员可以按时到位。若多项工作共用同一组人员，还需要安排人员的使用顺序。

### 正推 Forward Pass：ES / EF

Forward Pass（正推）按活动顺序从前往后计算。Early Start（ES，最早开始）是全部紧前工作完成后可以开始的最早时间；Early Finish（EF，最早完成）等于ES加上工期d。

起点ES=0；ES=max(紧前活动的EF)；EF=ES+d；项目总工期T=max(末端活动的EF)。max表示取最大值。

例子：C（安装电脑和取号设备）在8完成，D（制作并安装指路牌）在7完成。E（检查设备和指路牌是否符合要求）要等两项都完成，所以ES=max(8,7)=8。检查需要1天，因此EF=9。

### AON活动框中的字段与缩写

**Slack / Float · 时差（浮时）**

安排项目时，有些工作可以适当延后。允许延后的时间有多少，取决于我们是否允许影响后续工作，以及是否允许影响项目完工。

**Total Slack (TS) / Total Float (TF) · 总时差**

在不推迟项目完工的情况下，一项活动允许延迟的时间。用最迟开始减去最早开始计算：TF=LS−ES；也可以用最迟完成减去最早完成：TF=LF−EF。九宫格中的SL记录这个总时差。

SL / Total Slack（TS）/ Total Float（TF）：总时差。Free Slack（FS）/ Free Float（FF）：自由时差。DUR / d：工期。

例子：B（设计指路牌）上排填2、B、5；中排填1及活动名称；下排填3、3、6；框外FF填0。

容易混淆的地方：FS有两个含义：依赖类型中的Finish-to-Start表示前项完成后后项才开始；时差计算中的Free Slack表示自由时差。本工具用FF标自由时差。

### 逆推 Backward Pass：LS / LF

末端活动LF=T；LF=min(紧后活动的LS)；LS=LF−d。min表示取最小值，T为项目完成时间。

### Critical Path / CPM · 关键路径与关键路径法

**Gantt Chart / Milestone · 甘特图 / 里程碑**

甘特图用横轴表示时间，每条横条表示一项活动从开始到完成的区间。里程碑是重要事件，例如“接待区检查通过”，工期为0。检查工作需要1天，检查通过则是这项工作完成后的一个时点。

例子：从确认要求，经安装电脑和取号设备，再到检查的A-C-E路径需要2+6+1=9天。从确认要求，经设计和制作并安装指路牌，再到检查的A-B-D-E路径需要2+3+2+1=8天。A-C-E是关键路径。

### PERT · 三点工期估计

**Probability of Completion / Due Date · 完工概率 / 目标期限**

项目经理提出“希望10天内完成”时，10天是目标期限，记为D。完工概率表示在这个期限前完成的可能性，取值从0到1，也可以写成百分比。

**Normal Approximation / Standard Normal Distribution · 正态近似 / 标准正态分布**

正态分布呈钟形，数值在平均值附近较集中，两侧较少。这里用正态分布近似计算这条路径的完成时间。标准正态分布将平均值记为0、标准差记为1，便于使用统一的概率表。

tₑ=(a+4m+b)/6；σ=(b−a)/6；σ²=((b−a)/6)²。

例子：某项安装工作a=2天、m=4天、b=8天。期望工期tₑ=(2+4×4+8)/6≈4.33天；标准差σ=(8−2)/6=1天；方差σ²=1天²。

容易混淆的地方：Expected Time（期望工期）是加权平均时间。Standard Deviation（标准差）表示波动程度，单位为天；Variance（方差）是标准差的平方，单位为天²。计算中保留精度，最后按题目要求舍入。

### Probability of Completion · 完工概率与期限

**Gantt Chart / Milestone · 甘特图 / 里程碑**

μ=Σtₑ；V=Σσᵢ²；σ=√V；Z=(D−μ)/σ；P≈Φ(Z)；D=μ+zₚσ。 Σ表示沿选定路径相加；√表示开平方。

例子：A（确认设备和指路牌的要求）按2天、E（检查设备和指路牌是否符合要求）按1天计算；C（安装电脑和取号设备）的期望为6.333…天、方差为1天²。因此A-C-E的μ=9.333…天、σ=1天。期限D=10时，Z≈0.667，按时完成概率约74.75%。

容易混淆的地方：按工期相互独立、路径保持关键、完成时间近似正态分布计算。路径方差先相加，再开平方得到标准差。单侧95%的z约1.645；有相关工期或其他竞争路径时，需要相应调整分析。

路径工期=沿路径各活动工期之和；关键路径工期=项目工期T。本例按最早完成时间逆推，关键活动的TF=0。

例子：从确认要求，经安装电脑和取号设备，再到检查的A-C-E路径需要2+6+1=9天。从确认要求，经设计和制作并安装指路牌，再到检查的A-B-D-E路径需要2+3+2+1=8天。A-C-E是关键路径。

## 5.2 依赖类型与滞后

把关系转换成时间条件后，5.3用甘特图检查它们在同一时间轴上是否成立。

### Dependency Relationship · 依赖关系

依赖关系明确两个活动的哪两个时间需要比较。I为提供条件的活动，J为受到限制的活动；S为开始，F为完成，d为工期。

F=S+d。FS比较Fᵢ与Sⱼ；SS比较Sᵢ与Sⱼ；FF比较Fᵢ与Fⱼ；SF比较Sᵢ与Fⱼ。

例子：安装开始2天后才可检查，对应SS+2，因为比较两个开始时间。

容易混淆的地方：关系规定不能早于的时间，不一定要求恰好同时发生。关系FF与Free Float自由时差的FF含义不同。

### Finish-to-Start（FS）· 完成-开始

I完成后，J才能开始。正滞后要求在I完成后额外等待。

Sⱼ≥Fᵢ+L=Sᵢ+dᵢ+L。

例子：刷墙从0到2，FS+1后安装指路牌：安装最早从3开始。

容易混淆的地方：J的工期不改变这个开始下界，只影响J的完成时间。

### Lead / Lag · 提前量与滞后量

正L表示指定时间之间至少保留的滞后，负L表示允许提前的量。工期与L分别记录。

FS−2：Sⱼ≥Fᵢ−2；FS+2：Sⱼ≥Fᵢ+2。

例子：安装从0到6，检查需3天，FS−2允许检查从4到7，两个工期均不改变。

容易混淆的地方：同样的数字放在FS或SS后，分别从完成或开始计算，不能互换。提前安排需要有可以分批或重叠工作的实际条件。

### Start-to-Start（SS）· 开始-开始

J不能早于I开始；有正滞后时，需要从I开始再等待L。

Sⱼ≥Sᵢ+L。

例子：安装从0开始，SS+2后开始检查：检查最早从2开始。

容易混淆的地方：SS+0允许同时开始，也允许后续更晚开始；仅有SS不能保证两项工作的完成顺序。

### Finish-to-Finish（FF）· 完成-完成

J的完成不能早于I的完成加上L。为求J的开始时间，需要减去J的工期。

Fⱼ≥Fᵢ+L；Sⱼ≥Fᵢ+L−dⱼ。

例子：安装在6完成，检查需3天，FF+0允许检查最早从3到6。

容易混淆的地方：FF限制完成，FS限制开始；不能把同一个时间直接同时填作两种关系的开始时间。

### Start-to-Finish（SF）· 开始-完成

I开始后，J才允许结束。常见于需要维持服务的交接安排。

Fⱼ≥Sᵢ+L；Sⱼ≥Sᵢ+L−dⱼ。

例子：新班在8开始，旧班需4小时，SF+0允许旧班从4到8；SF+1则最早从5到9。

容易混淆的地方：J可能在I之前开工。箭头表示谁为谁提供条件，不单由实际开工先后决定。

### Lead / Lag · 提前量与滞后量

正L表示指定时间之间至少保留的滞后，负L表示允许提前的量。工期与L分别记录。

FS−2：Sⱼ≥Fᵢ−2；FS+2：Sⱼ≥Fᵢ+2。

例子：安装从0到6，检查需3天，FS−2允许检查从4到7，两个工期均不改变。

### 多个关系的合并

将每个前置条件换成J的开始时间下界，然后取最大值。还要满足项目起点等其他下界。

## 5.3 甘特图与进度基线

时间图显示工作安排；主题8还要逐时段核对这些横条是否需要超过可用容量的人员。

### Gantt Chart / Milestone 甘特图／里程碑

**Gantt Chart · 甘特图**

用横条表示活动开始、持续和完成时间的图。横轴是时间，纵向列出活动，横条长度按工期比例绘制。

**Milestone · 里程碑**

项目中的重要事件或状态，工期为0，常用菱形表示。例如“接待区检查通过”。检查工作本身需要1天，不能因为结果重要就把检查活动写成0天。

条长＝完成−开始；从时间0开始计时，工期等于完成时间减开始时间，不额外加1。

|活动|开始|工期|完成|
|---|---|---|---|
|A 确认设备和指路牌的要求|0|2|2|
|B 设计指路牌|2|3|5|
|C 安装电脑和取号设备|2|6|8|

|E 检查设备和指路牌是否符合要求|8|1|9|


例子：检查从8至9持续1天，“检查通过”在9以菱形表示。

基线保留批准的安排；当前计划反映调整后的预计执行时间。

FS零滞后：后项开始≥每项紧前的完成。

例子：B推迟1天后要同步检查D，不能只移动一根横条。

容易混淆的地方：当前预测不能冒充实际完成；变更当前安排不自动修改批准基线。

## 5.4 AOA与虚活动

AON与AOA应保留同一组真实活动依赖。比较结果之前先核对逻辑，再检查工期和时差。

### AOA / Event 活动箭线法／事件

**Activity-on-Arrow (AOA) / Event · 活动箭线法／事件**

AOA的箭头表示活动并标出工期；圆形节点表示事件，事件本身不占用工期。箭尾事件发生后，活动才能开始；指向同一事件的所有活动都完成后，这个事件才能发生。

终点事件要等所有进入该事件的活动完成。

|活动|工期（天）|紧前活动|
|---|---|---|
|A 确认服务窗口及编号|2|无|
|B 测量指路牌安装位置|3|无|
|C 配置取号设备|4|A|
|D 制作指路牌|2|A、B|
|E 联合检查|1|C、D|


例子：A完成后可做C；D还需等B，不应让C和D共用相同开始事件。

容易混淆的地方：节点编号不代表时间，AOA不能按AON节点含义读取。

### Dummy Activity 虚活动

**Dummy Activity · 虚活动**

AOA中用于表达前置条件、工期和工作量均为0的活动，通常画成虚线。它使不同工作能够保留不同的前置条件。

工期0、工作量0；仍须核对方向与依赖。

|箭线|作用|
|---|---|
|A：1→2；B：1→3|两项工作可从起点分别开始|
|虚活动：2→3|事件3除了等B，还要等A完成|
|C：2→4；D：3→4|C只等A，D等A与B|
|E：4→5|C与D均完成后进行联合检查|


例子：虚线2→3使D同时等A和B，C仍只等A。

容易混淆的地方：零工期不表示可以删除，也不保证一定不在关键路径上。

### AOA事件正推与逆推

**Earliest Event Time / Latest Event Time · 事件最早时点／事件最迟时点**

事件最早时间是指向它的所有活动最早全部完成的时间；事件最迟时间是在不推迟项目规定完成时间的条件下，允许它最晚发生的时间。

Eⱼ=max(Eᵢ+dᵢⱼ)；Lᵢ=min(Lⱼ−dᵢⱼ)。

|事件|正推过程|E|L|
|---|---|---|---|
|1|项目起点|0|0|
|2|0+2|2|2|
|3|max(0+3, 2+0)|3|4|
|4|max(2+4, 3+2)|6|6|
|5|6+1|7|7|


例子：事件3取max(3,2)=3；事件2逆推取min(2,4)=2。

容易混淆的地方：虚活动也参与计算；不能忽略零工期箭线的逻辑。

### AOA活动TF与FF

**Activity Total Float in AOA · AOA活动总时差**

对于活动i→j，最早开始为Eᵢ，最迟完成为Lⱼ，因此总时差TF=Lⱼ−Eᵢ−d。

TF=Lⱼ−Eᵢ−d；FF=Eⱼ−Eᵢ−d。

例子：Eᵢ=2，Eⱼ=7，Lⱼ=9，d=4时，TF=3，FF=1。

容易混淆的地方：事件余量L−E与活动总时差不是同一个量。

## 6.1 人工与工作量的成本估算

估算说明需要多少成本，6.2把费用安排到期间，再比较提前完工的代价。

### Cost Classification 成本分类

**Direct Cost / Indirect Cost · 直接成本／间接成本**

直接成本可以明确归属于指定成本对象；间接成本用于支持多个工作或项目，需要按既定依据分配。分类取决于所选成本对象和核算规则。

先定成本对象，再定直接／间接；不同维度可同时成立。

|分类维度|含义|医院例子|
|---|---|---|
|Direct / Indirect 直接／间接|是否可直接归入该成本对象|专用于本项目的终端采购；支持多个项目的办公室费用|
|Recurring / Nonrecurring 经常／非经常|是否在相同工作中反复发生|每周设备租金；一次性设计设置费|
|Fixed / Variable 固定／变动|在给定范围内是否随数量变化|固定进场费；按安装台数计费|
|Normal / Expedited 正常／加速|正常节奏或加速执行下的费用|普通运输费；加急运输附加费|


|费用来源|医院项目中的例子|
|---|---|
|Labor 人工|配置人员和安装人员的工时费用|
|Materials 材料|线材、固定件等耗用材料|
|Subcontractors 分包|委托专业单位制作并安装标牌|
|Equipment and Facilities 设备与设施|取号终端采购、测试设备或场地租用|
|Travel 差旅|项目人员为现场检查发生的交通与住宿费用|


例子：按每台500元收取的安装费可同时是直接、变动成本。

容易混淆的地方：分类随成本对象与政策确定，不能只凭费用名称。

### Fully Burdened Labor 满载人工

**Fully Loaded / Fully Burdened Labor Cost · 满载人工成本**

在直接人工工资上，加入规定的人工附加费用后的人工成本。使用费率前先确认它已经包括哪些费用。

工资×工时×(1+h)，或工资×工时×已给乘数。

例子：200元/小时×40小时×1.60=12,800元。

容易混淆的地方：附加率0.60与总乘数1.60不同；已含费用不要重复加入。

### 成本、应急与报价

**Contingency Reserve · 应急储备**

为估算中的相关不确定性预留的费用。例如，安装方案可能需要额外配件，估算时为这类变化预留金额，并说明使用依据。

**Profit / Price · 利润／报价**

利润是报价中超过相应成本的部分；报价是供应商向客户提出的总金额。利润按成本加成10%和占最终售价10%使用不同基数，因此必须先说明计算口径。

成本加成报价＝包含应急储备的成本×(1＋利润加成率)。

例子：包含应急储备的成本22000，加成10%，报价24200。

容易混淆的地方：成本加成率与售价利润率不同；先写计算基数。

### Top-down / Bottom-up 估算方法

**Top-down / Bottom-up Estimating · 自上而下／自下而上估算**

自上而下利用整体规模、历史项目和比例作早期估计；自下而上分别估算较细的工作包，再汇总为项目估算。

比率法＝数量×单位成本；分摊法＝总额×比例。

|方法|计算思路|例子与条件|
|---|---|---|
|Ratio Method 比率法|数量×可比单位成本|120平方米×每平方米2000元=240000元；核对装修标准和包含范围|
|Apportion Method 比例分摊法|总估算×历史分项比例|总额200000元，标牌占5%，分配10000元；历史项目须可比|
|Bottom-up 自下而上|逐工作包估算后汇总|分别估计设备、标牌、测试和培训，核对重复与遗漏|


例子：120平方米×2000元/平方米=240000元。

容易混淆的地方：历史标准、范围与价格口径需要可比；细表不等于可靠依据。

### Learning Curve 第X单元学习曲线

**Learning Curve · 学习曲线**

在重复、相似工作中，用学习率估计后续单元所需时间。学习率表示数量翻倍时，第2X单元用时相对于第X单元的比例。

Yₓ=aXᵇ，b=log(r)/log2；总工时=ΣYₓ。

例子：a=40，r=.9时，Y₂=36，Y₄=32.4。

容易混淆的地方：翻倍保留r倍用时；第X单元不是前X单元累计平均。

### 学习曲线反推与累计

已知后续单元用时，先反推首项，再逐项累计。

a=Yₓ/Xᵇ；费用=累计工时×费率×负担乘数。

例子：第4次40小时、90%学习率，首次49.3827，四次共175.6151。

容易混淆的地方：不要把第X次、累计平均、累计总量或日历工期混为一谈。

### Function Point 功能点

**Function Point (FP) · 功能点**

按功能类型、数量与复杂度权重计算的软件规模指标。功能点本身不是天数，也不是代码行数。

FP=Σ数量×权重；人月=FP/生产率；成本=人月×费率。

|功能类型|医院软件中的例子|低|中|高|
|---|---|---|---|---|
|Inputs 输入|工作人员录入患者登记信息|2|4|6|
|Outputs 输出|生成每日接待汇总报告|4|6|10|
|Interfaces 接口|与收费系统交换已确认资料|3|7|12|
|Queries 查询|按号码查询当前等候信息|5|10|15|
|Files 文件|保存和维护登记记录|2|4|8|


例子：45 FP、15 FP/人月，得到3人月。

容易混淆的地方：权重使用题目给定表；人月不能直接等同于日历月。

## 6.2 预算安排与工期压缩

成本最小不一定满足硬性期限。决策还要结合风险与资源，不能只选表中最小的一个数。

### Activity Budget / ABC 活动预算／作业成本法

**Activity-based Costing (ABC) · 作业成本法**

把成本与产生资源消耗的活动联系起来，并按活动成本动因分配相关费用。本专题先练习把人员、材料等成本落实到活动。

数量×费率→活动成本→项目合计；共享费用不重复。

|活动|资源依据|预算（元）|
|---|---|---|
|确认设备和指路牌要求|协调与设计人员工时|2000|
|制作并安装指路牌|材料、制作与安装|3000|
|安装电脑和取号设备|设备及安装配置资源|6000|


例子：协调费3000分配到三项工作后合计仍为3000。

容易混淆的地方：成本发生、付款与活动执行时间可能不同，应说明时间分布口径。

### Time-phased Budget 时间分布预算

**Time-phased Budget / Cost Baseline · 时间分布预算／成本基线**

把批准的预算按预计发生时间分配，形成每期与累计计划金额。它既说明总额，也说明计划在何时消耗这些金额。

行合计＝活动预算；列合计＝期间金额；累计＝此前各期之和。

|活动|第1周|第2周|第3周|合计|
|---|---|---|---|---|
|确认要求|2000|0|0|2000|
|制作并安装指路牌|1000|2000|0|3000|
|安装并配置设备|0|2000|4000|6000|
|每周合计|3000|4000|4000|11000|
|累计计划|3000|7000|11000|—|


例子：每周3000、4000、4000，对应累计3000、7000、11000。

容易混淆的地方：总额相同不代表任意状态日期的计划金额相同。

### 费用比较与符号

**Cost Comparison · 费用比较**

先对齐工作范围、统计日期和费用项目，再比较计划与实际。这里采用实际−计划，正数表示多花，负数表示少花。

本页：实际−计划；挣值CV：EV−AC。

例子：计划7000、实际7600，费用差额+600。

容易混淆的地方：少花可能来自少完成工作，不能只比较支出就断言绩效。

### Crashing / Cost Slope 赶工／成本斜率

**Crashing / Cost Slope · 赶工／成本斜率**

赶工通过额外资源等办法缩短工期。成本斜率表示在给定线性区间内，每缩短一个时间单位增加的直接成本。

斜率=(赶工费−正常费)/(正常工期−最短工期)。

例子：6天1500元压到3天2100元，斜率200元/天。

容易混淆的地方：先确认可压缩区间与成本模型，再检查当前关键路径。

### 逐轮赶工与多关键路径

以当前网络重新识别关键路径，再选择有效压缩组合。

每轮：找关键路径→比较可行增量成本→压缩→重算。

|活动|紧前|正常→最短工期|正常→赶工费|斜率|
|---|---|---|---|---|
|A 确认要求|无|2→1|600→900|300元/天|
|B 指路牌准备|A|4→2|800→1000|100元/天|
|C 设备安装|A|6→3|1500→2100|200元/天|
|D 联合检查|B、C|1→1|400→400|不可压缩|


例子：两条关键路径时，压共同活动或同时覆盖各条路径。

容易混淆的地方：最便宜的非关键活动不一定能缩短项目；每轮关键路径可能变化。

### Fast-tracking / Crashing 快速跟进／赶工

**Fast-tracking · 快速跟进**

让原本先后执行的工作部分重叠，以缩短项目历时。例如图样分区确认后，先制作已经确认的部分，不必等待所有图样全部完成。

快速跟进核对信息、接口和返工；赶工核对资源、成本和最短工期。

|方案|直接改变什么|要核对什么|
|---|---|---|
|增加安装班组|安装活动的工期和成本|工作面、效率、协调及最短工期|
|图样分区批准后开始制作|设计与制作之间的依赖|已确认范围、接口、返工风险|
|单纯修改计划完成日期|没有改变可执行安排|不能因此获得真实的工期缩短|


例子：分区图样确认后先制作已确认部分属于快速跟进。

容易混淆的地方：单纯改日期不产生工期缩短；必要技术等待不能任意删除。

## 7.1 识别、评估与处理项目风险

风险记录中的等待和替代方案会改变进度、成本与资源安排，需要回到同一份计划核对。

### Risk / Issue 风险／问题

**Risk · 风险**

可能发生并影响项目目标的不确定事件或条件。设备可能晚到会威胁开放日期；设备可能提前到货也可能带来提前测试的机会。正面与负面的不确定性都需要分析。

**Issue · 问题**

已经发生、需要处理的情况。供应商确认晚交3天后，这3天延期已经是问题；是否还会进一步晚交，仍是不确定的风险。

识别→评估→应对→控制；随新信息更新状态。

例子：已确认晚3天作为问题，进一步延期仍可作为风险。

容易混淆的地方：不能把已发生事实继续只当作可能性，也不能把机会当作既得收益。

### 风险的原因、事件与后果

**Cause–Event–Effect · 原因、事件与后果**

原因说明风险来源或条件，事件说明可能发生什么，后果说明对项目范围、时间、成本、质量等目标的影响。

因某条件，可能发生某事件，导致某目标受影响。

|部分|设备交付风险|
|---|---|
|原因|关键零件只有一家供应商，备用库存不足|
|事件|供货中断导致取号设备未能按时到货|
|后果|安装和联合测试推迟，可能影响开放日期|


例子：图样未及时确认→错过制作班次→安装可能晚2天。

容易混淆的地方：“项目失败”等笼统后果不足以指向监测与应对。

### RBS 风险分解结构

**Risk Breakdown Structure (RBS) · 风险分解结构**

按风险来源分层组织风险的结构，用于系统识别和检查遗漏。WBS分解项目工作，RBS分解风险来源，两者可以交叉检查。

类别说明来源；风险记录写具体事件与影响。

|一级来源|二级来源|具体事件|
|---|---|---|
|外部|供应与商业|供应商生产安排变化，设备可能晚到|
|外部|合同与法规|审批条件可能变化，导致补充工作|
|内部|技术与接口|终端与叫号系统接口可能不兼容|
|内部|执行与协调|测试人员安排冲突，可能错过验收窗口|
|内部或外部|财务|付款安排或价格变化可能影响采购|


例子：设备安装包可同时检查供应、技术接口和人员安排风险。

容易混淆的地方：RBS不是活动顺序图，同一事件跨类别不能重复计损失。

### Probability–Impact Matrix 概率影响矩阵

**Probability–Impact Matrix · 概率影响矩阵**

用发生可能性和后果严重程度交叉定位风险，辅助确定管理优先级。等级应有明确含义与判断依据。

先读坐标和尺度，再按该矩阵规则判等级。

|等级|本练习可能性定义|本练习工期影响定义|
|---|---|---|
|1 低|估计概率低于20%|延期不超过1天|
|2 中|估计概率20%至50%|延期超过1天且不超过3天|
|3 高|估计概率超过50%|延期超过3天|


例子：P等级2、I等级3，乘积6为本练习高优先级。

容易混淆的地方：等级乘积不是失败概率，也不是期望货币损失。

### RF Risk Factor 风险因子

**Risk Factor (RF) · 风险因子**

由失败可能性评分Pf与失败后果评分Cf合成的项目风险评分。Pf和Cf在这里是评分结果，不应直接当作经过统计验证的失败概率。

Pf=均值；Cf=均值；RF=Pf+Cf−PfCf。低<.30，中.30至.70，高>.70。

|评分|组成|
|---|---|
|Pf：Probability of Failure score|Pm Maturity成熟度、Pc Complexity复杂性、Pd Dependency依赖程度的平均|
|Cf：Consequence of Failure score|Cc Cost成本、Cs Schedule进度、Cr Reliability可靠性、Cp Performance性能后果评分的平均|


例子：Pf=.5、Cf=.4，RF=.70为中风险。

容易混淆的地方：RF不等于PfCf，也不是实际失败概率。

### 风险模型选择

**Expected Monetary Value (EMV) · 期望货币值**

当事件概率与金额后果有明确口径时，用各结果的概率乘对应金额并相加。下面只讨论一个损失事件，采用正数表示预期损失。

单项期望损失=P×损失金额；先确认P为概率。

|模型|所需输入|结果含义|
|---|---|---|
|概率影响矩阵|已定义的等级及排序规则|相对管理优先级|
|RF|规定的项目评分项|项目风险因子等级|
|期望损失|事件概率与损失金额|多次同类情境下的平均损失估计|


例子：20%×10000元=2000元期望损失，发生时仍损失10000。

容易混淆的地方：期望值不是单次上限，不要把等级3直接解释为30%。

### Risk Responses 风险应对

**Risk Response · 风险应对**

为改变风险的来源、发生可能性、后果或承担责任而采取的行动。先说明想改变什么，再选择措施。以下五种策略对同一个交期风险采取不同处理。

**Insurance · 保险**

通过合同把约定的经济后果转给保险方承担。赔付范围、免赔条件和未被补偿的工期影响需要分别检查；得到赔偿不等于恢复了开放日期。

**Workaround · 临时应变措施**

问题发生后，没有现成预定方案可直接使用时，团队临时制定的处理办法。例如设备确认晚到后，负责人临时安排人工登记。若团队早已规定何时改租备用设备，那属于事先准备的应急计划。

避免、减轻、转移、接受、分担；实施后检查残余与次生风险。

|策略|设备到货例子|仍需关注|
|---|---|---|
|Avoid 避免|取消依赖该进口型号，采用已确认可用现货|替代方案是否满足要求|
|Minimize / Mitigate 减轻|提前检查生产节点，准备可替换设备|剩余概率和替换实施条件|
|Transfer 转移|约定延迟赔偿或保险责任|赔偿不能自动恢复开放日期|
|Accept 接受|确认影响可以承受，规定什么时候启动后备方案|准备谁来做什么|
|Share 分担|与合作方共同备货和承担约定成本|责任边界与协调机制|


例子：赔偿分配费用责任，不能自动恢复延期。

容易混淆的地方：“接受”可以包含监测和应急准备，不等于无人管理。

### Contingency 储备与应急

**Contingency Plan · 应急计划**

预先规定某个条件出现后采取的行动。例如，第5天仍无出厂证明时，由采购负责人确认备用设备，并报告能否维持第9天安装。

**Contingency Reserve · 应急储备**

为相关不确定性预留的费用或时间。例如，为备用设备租赁预留3000元，并明确采购负责人何时可以使用、需由谁批准。储备提供资源，应急计划说明如何行动。

总额=基数×乘数；增量=基数×(乘数−1)。

例子：20000×1.15=23000，储备3000。

容易混淆的地方：总额不能再次加到基数上；储备大小不能代替触发和责任。

### PRAM 项目风险分析与管理

**Project Risk Analysis and Management (PRAM) · 项目风险分析与管理**

贯穿项目的风险分析和管理过程，强调分析目的、责任、措施与后续管理之间的联系。

Define、Focus、Identify、Structure、Ownership、Estimate、Evaluate、Plan、Manage。

|阶段|在设备延迟风险中做什么|
|---|---|
|Define 定义|明确项目目标、交付物和计划|
|Focus 聚焦|确定本次分析的范围、深度与方法|
|Identify 识别|找出关键零件短缺等来源和事件|
|Structure 组织|梳理风险之间及与工作之间的关系|
|Ownership 明确归属|指定采购负责人及相关责任|
|Estimate 估计|估计概率、影响与措施效果|
|Evaluate 评价|比较结果和优先级|
|Plan 规划|制定应对、触发条件和资源安排|
|Manage 管理|执行监测、复查实际效果并更新|


例子：先估计不同措施效果，再评价选择，最后监测实施。

容易混淆的地方：Estimate提供估计，Evaluate作评价；登记结束不等于管理结束。

### Risk Register 风险登记册

**Risk Register · 风险登记册**

持续记录风险事件、评估依据、应对措施和实际结果的资料。每一行应能说明有什么风险、谁在跟进、接下来何时做什么。

**Risk Owner · 风险负责人**

负责跟踪某项风险、协调措施并更新信息的人。例如，采购负责人跟踪设备交期，安装负责人评估对现场工作的影响。

**Trigger · 触发条件**

用来判断何时启动某项行动的可观察条件。例如，“第5天仍未收到出厂证明”包含日期和证据，比“风险变大时”更容易判断。

记录原因事件后果、评估、负责人、触发、行动、复查和结果。

|字段|本例内容|
|---|---|
|风险描述|零件短缺可能导致设备晚到，影响安装和开放|
|评估依据|供应商生产节点与历史交付记录|
|负责人|采购负责人|
|措施与触发|第5天仍无出厂证明，启动替代确认|
|下一次复查|第5天；收到新交期时立即更新|
|实际结果|是否取得证明、措施是否启动、最终到货与影响|


例子：第5天无出厂证明，由采购负责人确认替代设备。

容易混淆的地方：字段齐全不代表策略有效，仍要核对措施与风险之间的关系。

## 8.1 单项目与多项目的资源安排

把资源顺序加入计划以后，8.2继续分析关键链，以及不同位置的缓冲保护什么。

### Resource Loading 资源负载

**Resource Loading · 资源负载**

一个时间段内，计划执行的全部工作合计需要多少同类资源。例如，同一天两项安装各需2人，该天的安装人员负载就是4人。

**Resource Capacity · 资源容量**

同一时间段内实际能够提供的资源数量或工时。本例安装队每天只有2人，负载4人超过容量2人，意味着当天的原安排无法同时执行。比较时要使用相同资源种类和时间单位。

负载=同时执行活动需求之和；过载=max(0,负载−容量)。

|工作|工期|每天需安装人员|紧前|
|---|---|---|---|
|A 准备接口|2|1|无|
|B 安装取号设备|3|2|A|
|C 安装显示屏|2|2|A|
|D 联合测试|1|1|B、C|


|约束类型|医院中的限制|
|---|---|
|Physical 物理约束|墙面需要达到安装条件后才能固定标牌|
|Time 时间约束|接待区必须在规定开放日期前可用|
|Resource 资源约束|同一时段只有两名合格安装人员|
|Mixed 混合约束|既有固定开放日期，又有人员和场地限制|


例子：B与C各需2人，同时做需4人，容量2则超出2人。

容易混淆的地方：逻辑可行不等于资源可行；总工时也不能代替逐日核对。

### Smoothing / Leveling 平滑／平衡

**Resource Leveling / Resource Smoothing · 资源平衡／资源平滑**

通过调整活动时段，减少资源过载或用量起伏。先确定题目允许改变什么：若完工日期固定，就在可用时差内移动工作；若资源容量固定且原日期不可行，就需要比较延期、增员或改变方法。Resource Smoothing常用于强调不改变完工期限的平滑安排；课程也将它作为Resource Leveling的别称，因此应以题目给定约束为判断依据。

每次移动后核对：依赖、容量、工作总量、完工时间。

例子：两项各需整支队伍的工作只能串行，可能延长原逻辑工期。

容易混淆的地方：有时差不保证能消除冲突；无冲突不保证依赖正确。

### Scheduling Heuristics 排程启发规则

**Scheduling Heuristics · 排程启发规则**

用较容易执行的规则选择活动顺序，例如最小总时差、最短工期、最多后继、最大资源需求或较小活动编号。它们帮助构造方案，不保证全局最优。

按最小总时差、最短工期等排序后，仍要检验完整排程。

|规则|何时优先|需要继续检查|
|---|---|---|
|Minimum Slack 最小总时差|延迟余地最小的活动|其他活动是否还能在可用窗口完成|
|Shortest Duration 最短工期|工期较短、能让执行人员较早开始下一项工作的活动|是否推迟长工期关键工作|
|Most Successors 最多后继|完成后有较多后续工作可以开始的活动|后续是否确实有资源开工|
|Lowest ID / First Come 较小编号／先到|按预先约定的编号或就绪顺序|只有编号代表到达顺序时，两种规则才一致|
|Greatest Resource Demand 最大资源需求|需要较多资源的活动优先|仍需检查可用容量与对其他活动交期的影响|


例子：TF0的测试优先于TF4的复查，但复查仍需安排在合法窗口。

容易混淆的地方：任何一种启发规则都不能自动证明全局最优。

### Task Splitting 任务拆分

**Task Splitting · 任务拆分**

在工作允许中断和恢复的条件下，把一项活动安排在多个不连续时段。总工作量仍应完成，并计入切换或恢复成本。

分别计算实际执行时长与从开始到完成的历时。

|安排|工作量|开始至最终完成的跨度|
|---|---|---|
|第2天查1组，第5至6天查2组|3个工作日|从第2天开始至第6天结束|
|连续三天检查|3个工作日|需找到连续3天可用窗口|


例子：1天执行＋2天停顿＋2天执行，工作量3天、跨度5天。

容易混淆的地方：拆分不自动创造容量；连续性要求和恢复成本不能忽略。

### Multiproject Scheduling 多项目排程

**Multiproject Resource Scheduling · 多项目资源排程**

在多个项目共享容量的条件下，安排资源顺序和各项目开始进入执行的时间，并比较各项目延期及整体完成表现。

延期=max(0,完成−目标)；同时比较等待和整体完成。

|项目|测试台占用|可开始|目标完成|
|---|---|---|---|
|A 接待区|3|0|5|
|B 药房|2|0|4|
|C 门诊叫号|4|0|10|


例子：A-B-C使药房晚1天，B-A-C可使三项均按目标完成。

容易混淆的地方：单项目独立计划不能消除共享资源冲突。

### WIP 在制工作与切换

**Work in Process (WIP) · 在制工作**

已经开始但尚未完成的工作或项目。多个项目同时启动却等待同一瓶颈，可能增加在制工作和协调负担。

总历时＝执行时间＋等待及切换时间。

例子：4天工作：连续做完甲再做乙需1次切换，共4.5天；甲乙交替需3次切换，共5.5天。

容易混淆的地方：减少WIP不自动减少本来必须执行的工作量。

### 多项目优先级与取舍

综合交期、价值、容量和准备条件确定共享资源顺序。First In Line先到先服务、Greatest Resource Demand最大资源需求、Greatest Resource Utilization最大资源利用、Minimum Late Finish Time最小最迟完成时间是可比较的规则；Mathematical Programming数学规划明确变量、目标与约束后求解。

规则→可执行性→指标比较→授权与共同日历。

|判断依据|需要的信息|
|---|---|
|交期风险|目标日期、延误后果、剩余工作|
|业务优先级|开放需求、批准的项目优先级|
|资源效率|占用时长、准备与切换成本|
|可执行性|资料是否齐全、前置是否完成、预约是否可用|


|资源分配规则|采用前需要判断什么|
|---|---|
|First In Line 先到先服务|以事先约定的到达或就绪顺序排队|
|Greatest Resource Demand 最大资源需求|优先满足需求量较大的项目，继续检查对其他项目的影响|
|Greatest Resource Utilization 最大资源利用|比较安排能否减少资源闲置，同时核对交期|
|Minimum Late Finish Time 最小最迟完成时间|优先最迟完成时点较早的工作；这个时点由网络或约束推得，不一定等于项目对外截止日期|
|Mathematical Programming 数学规划|把选择或开始时间设为变量，写出容量、依赖等约束，再按选定目标求解|


例子：最早期限项目未准备好时，不能让瓶颈无限空等。

容易混淆的地方：不同规则不保证同一目标最优，需说明选择与代价。

## 8.2 关键链与时间缓冲

缓冲大小、放置位置与资源可行性要一起检查。算出一个正数，并不表示计划已经可执行。

### TOC 约束理论

**Bottleneck · 瓶颈**

限制整个流程产出的环节。本例每台终端都要安装、配置和测试；即使前两步每天能处理更多，测试每天只能完成3台，最终交付仍受它限制。

**Theory of Constraints (TOC) · 约束理论**

围绕当前限制整体产出的约束组织改进：先识别约束，充分利用现有能力，让其他环节配合，再提升约束能力，并重新寻找下一处限制。

Identify→Exploit→Subordinate→Elevate→Repeat。

|步骤|在测试环节中的做法|
|---|---|
|Identify 识别约束|找出每天只能测试3台的限制|
|Exploit 充分利用现有约束|提前准备资料，减少测试台空等和返工|
|Subordinate 其他环节配合|安装与配置按测试能力和缓冲安排节奏|
|Elevate 提升约束能力|需要时增加测试能力或改进测试方法|
|Repeat 重复|测试提高后，重新找限制整体的环节|


例子：8、6、3台/天串行流程受测试3台/天限制。

容易混淆的地方：局部利用率提高不必然增加整体产出，瓶颈也会转移。

### Critical Chain 关键链

**Critical Chain Project Management (CCPM) / Critical Chain · 关键链项目管理／关键链**

关键链是同时考虑工作先后关系和资源约束后，决定项目完成时间的活动链。关键链项目管理还把为不确定性预留的时间集中为缓冲，并在执行中跟踪使用情况。

**50% Probability Duration · 50%完成概率的工期估计**

如果一项活动的估计工期为6天，且有50%的可能在6天内完成，这描述的是工期分布中的中间位置。它不等于把任何原估计机械除以2，也不表示项目有50%的缓冲。活动估计与后面按链长50%设置缓冲，是两个不同概念。

先处理资源冲突，再识别关键链和安排缓冲。

|比较对象|关键路径CPM|关键链CCPM|
|---|---|---|
|识别依据|活动逻辑与工期；标准网络先算逻辑时间|活动逻辑、资源顺序及所采用的工期估计|
|余量与保护|根据网络计算总时差与自由时差|把安全时间集中成不同位置的缓冲|
|资源|需要另行核对资源可行性|识别关键链时已处理资源冲突|


例子：同一安装队使3天与2天工作串行，项目从逻辑6天变为8天。

容易混淆的地方：资源顺序不是不可改变的技术依赖；关键链与关键路径不总相同。

### Project / Feeder (Feeding) Buffer 项目／馈入缓冲

**Project Buffer (PB) · 项目缓冲**

安排在关键链末端与承诺交期之间的保护时间。关键链上的延迟会消耗这段时间，项目经理据此判断承诺日期是否受到威胁。

**Feeder Buffer / Feeding Buffer (FB) · 馈入缓冲**

安排在非关键支路完成后、汇入关键链之前的保护时间。它为支路延迟留出余地，保护关键链的汇合点。两种英文写法都指这里的支路缓冲。

50%规则例：主链45→PB22.5；汇入关键链的支路15→FB7.5。

|时间量|怎样得到|保护对象|
|---|---|---|
|Total Float 总时差|根据活动依赖、工期和规定完成时间计算|不推迟项目结束的活动延迟余地|
|Project Buffer 项目缓冲|按选定方法主动安排|最终交期|
|Feeder Buffer 馈入缓冲|在非关键支路接入关键链之前预留|关键链上的汇合点|


例子：主链含项目缓冲67.5天；馈入缓冲安排在支路汇入前。

容易混淆的地方：50%是选定估算规则，不能把所有项目都机械砍半；TF也不是缓冲。

### Buffer Sizing 缓冲估计

**Buffer Sizing / Buffer Management · 缓冲大小估计／缓冲管理**

前者确定预留保护时间，后者在执行中观察缓冲消耗与工作完成情况，及时处理对交期的威胁。

**Central Limit Theorem · 中心极限定理**

在适当的独立性与分布条件下，多项随机用时的总和可以趋近正态分布。把保护时间集中安排时，可以考虑并非每项活动都会同时用尽自己的预留时间；但共同原因造成的相关延迟仍要另外分析。这个原理本身不规定缓冲一定取链长的一半。

50%链长法与B=√Σsᵢ²使用不同输入，题目系数另行处理。

例子：安全余量3、4天按平方和开方得到5天。

容易混淆的地方：不反复对已调整工期减半；安全余量不是自动等于PERT标准差。

### Drum / CCB 多项目瓶颈缓冲

**Drum Resource · 瓶颈资源**

限制多个项目整体执行节奏的共享资源。例如，医院各项目都必须使用且容量不足的测试台。协调者据此安排项目何时进入测试。

**Drum Buffer · 瓶颈前缓冲**

在项目使用瓶颈资源之前留出的准备保护时间。例如，测试预约在时点8，前面留1天缓冲，就要求上游工作在时点7准备好，以减少测试台等待输入的风险。

**Capacity Constraint Buffer (CCB) · 容量约束缓冲**

在不同项目使用同一瓶颈资源之间留出的间隔，减少前一项目超时对后一项目的影响。若甲在7结束、间隔1天，乙最早从8开始。课程中也出现CCP这一缩写，识别时按它所在的位置与作用判断。

先消除资源重叠，再决定前置保护、项目间隔和末端保护。

|安排|目的|
|---|---|
|项目A测试前的Drum Buffer|降低A上游延迟导致测试台空等的风险|
|A与B测试占用之间的CCB|减少A占用超时向B传递的冲突|
|项目B末端的Project Buffer|保护B自身承诺交期|


例子：A测试前设准备保护，A与B测试之间设CCB。

容易混淆的地方：项目末端缓冲不能消除共享资源冲突；需检验估计依据和实施条件。
